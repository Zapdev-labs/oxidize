# Research Report: exo (exo-explore/exo) Peer-to-Peer Distributed Inference Mesh Protocol

## Executive Summary

exo is a distributed AI inference system that connects heterogeneous consumer devices (Macs, PCs, phones, SBCs) into a unified cluster for running large language models. It uses a **hybrid Rust+Python architecture** where the networking and peer discovery stack is implemented in Rust (via `rust-libp2p`), while the orchestration, model placement, and inference execution are in Python on top of Apple's **MLX distributed** framework.

---

## 1. Peer Discovery

### Mechanism: libp2p + mDNS + GossipSub

exo uses a **Rust-based networking stack** (via `exo_pyo3_bindings`) that wraps the `rust-libp2p` library for peer discovery and messaging. The discovery pipeline is:

1. **libp2p Swarm**: Each node runs a libp2p swarm that advertises itself on the local network.
2. **mDNS (Multicast DNS)**: Used for local network peer discovery. Nodes broadcast their presence and listen for other peers.
3. **GossipSub**: Once peers are discovered, they subscribe to shared pub/sub topics for cluster-wide communication.

### Discovery Flow (from source)

```
libp2p Swarm (Rust)          NetworkingHandle (Rust)         Router (Python)
      |                             |                              |
      | FromSwarm::Discovered       | PyFromSwarm.Connection       | CONNECTION_MESSAGES
      | { peer_id }  -------------> | (peer_id, connected=True) -> | topic update
      |                             |                              |
      v                             v                              v
   Peer discovered           Python event emitted         TopologyEdgeCreated event
```

### Key Components

| Component | File | Purpose |
|-----------|------|---------|
| `NetworkingHandle` | `rust/exo_pyo3_bindings/src/networking.rs` | Translates libp2p swarm events into Python objects |
| `Router` | `src/exo/routing/router.py` | Manages GossipSub topics and forwards peer events |
| `ConnectionMessage` | `src/exo/routing/connection_message.py` | Event type for peer connect/disconnect |

### Namespace Isolation

The macOS app supports a custom namespace feature via `EXO_LIBP2P_NAMESPACE` environment variable to isolate clusters on the same network (e.g., dev vs. production clusters).

### Historical Note

Earlier versions used **UDP broadcasting** for peer discovery (issue #187), but this was not supported on cloud platforms. The current libp2p/mDNS approach is platform-agnostic and works across local networks.

## 2. Communication Protocol

### Two-Layer Architecture

exo separates **control plane** (orchestration) from **data plane** (tensor communication):

#### Control Plane: libp2p GossipSub

The `Router` registers **6 core pub/sub topics** that form the cluster's messaging backbone:

| Topic | Symbol | Description |
|-------|--------|-------------|
| `GLOBAL_EVENTS` | `topics.GLOBAL_EVENTS` | Master-indexed events broadcast to all nodes |
| `LOCAL_EVENTS` | `topics.LOCAL_EVENTS` | Un-indexed events from Workers to Master |
| `COMMANDS` | `topics.COMMANDS` | External requests (inference, placement) |
| `ELECTION_MESSAGES` | `topics.ELECTION_MESSAGES` | Leader election protocol messages |
| `CONNECTION_MESSAGES` | `topics.CONNECTION_MESSAGES` | Peer discovery and topology updates |
| `DOWNLOAD_COMMANDS` | `topics.DOWNLOAD_COMMANDS` | Model download coordination |

Messages are serialized and broadcast via GossipSub. The `EventRouter` manages local event sequencing, NACKs, and synchronization with the global log.

#### Data Plane: MLX Distributed Backends

For actual tensor communication during inference, exo delegates to **MLX's distributed communication library**. Two backends are supported:

| Backend | Transport | Use Case | Environment |
|---------|-----------|----------|-------------|
| **MLX Ring** | TCP/IP sockets | Standard network (WiFi/Ethernet/Thunderbolt) | `MLX_HOSTFILE` JSON |
| **MLX Jaccl** | RDMA over Thunderbolt 5 | Ultra-low-latency clusters | `MLX_JACCL_COORDINATOR`, `MLX_IBV_DEVICES` |

**MLX Ring**:
- Ring all-reduce and all-gather over TCP sockets.
- Rank `i` can only communicate with rank `i-1` and `i+1`.
- Hostfile JSON defines SSH hostnames and listening IPs per node.
- Dynamically generated by exo's Placement Engine for each model instance.

**MLX Jaccl** (Jack and Angelos' Collective Communication Library):
- Uses macOS 26.2+ RDMA over Thunderbolt 5.
- Requires a **fully connected mesh** (every node directly cabled to every other node).
- `MLX_IBV_DEVICES` JSON matrix maps `matrix[i][j]` to the RDMA device name on node `i` used to reach node `j`.
- Achieves ~99% latency reduction vs. TCP/IP for tensor parallelism.

**Other MLX backends** (not primary for exo but available):
- **NCCL**: For CUDA multi-GPU/multi-node environments.
- **MPI**: For general-purpose HPC clusters.

## 3. Model Sharding Strategies

exo supports three sharding strategies defined by the `Sharding` enum:

### Pipeline Parallelism

**Concept**: Splits a model's layers into contiguous ranges, assigning each range to a different node. Activations flow sequentially through the pipeline.

```
Input Tokens
    |
    v
Node 0 (Rank 0) --- mx.distributed.send ---> Node 1 (Rank 1) --- mx.distributed.send ---> Node 2 (Rank 2)
Layers 0-10                                Layers 11-20                                Layers 21-31
    |                                                                          |
    <--------------------------- mx.distributed.all_gather ----------------------|
                                                                               v
                                                                         Output Logits
```

**Implementation**:
- Layer ranges allocated proportionally to each node's available memory (`allocate_layers_proportionally`).
- `PipelineFirstLayer` and `PipelineLastLayer` wrappers handle `recv_like()` and `send()` boundaries.
- **Staggered prefill**: `pipeline_parallel_prefill` overlaps computation and communication to prevent bubbles.
- **Deadlock prevention**: `eval_with_timeout` (60s default) kills hung MLX operations to prevent cluster-wide GPU deadlocks.

**Metadata**: `PipelineShardMetadata(start_layer, end_layer, device_rank, world_size)`

### Tensor Parallelism

**Concept**: Splits weight tensors within each layer across multiple nodes. All nodes process all layers, but each holds a fraction of the weights (e.g., 1/N of attention heads).

```
Layer N - Attention
    |
    +-- Node 0: Q/K/V heads 0-15
    +-- Node 1: Q/K/V heads 16-31
    |
mx.distributed.all_sum()  <-- combines partial outputs
    |
Output (B, T, H)
```

**Implementation**:
- Uses MLX's `shard_linear` and `shard_inplace` functions.
- Model-specific strategies:
  - **Llama/Mistral**: `LlamaShardingStrategy` shards Q/K/V/O and MLP projections.
  - **DeepSeek V3/V3.2**: `DeepseekShardingStrategy` handles LoRA attention and MoE experts.
  - **Qwen/GLM MoE**: `QwenShardingStrategy` shards sparse MoE blocks with `all_sum` on expert outputs.
- **Constraints**: Model card must have `supports_tensor=True`. `hidden_size` and `num_key_value_heads` must be divisible by world size.

**Performance**: Up to 1.8x speedup on 2 devices, 3.2x on 4 devices (with RDMA).

### CFG Parallelism (Image Models)

For diffusion models (e.g., FLUX), exo can shard the **positive and negative prompt branches** across different nodes. `CfgShardMetadata(is_positive)` defines branch assignment.

### Performance Trade-offs

| Strategy | Memory Efficiency | Prefill Latency | Decode Latency | Network Requirement |
|----------|-------------------|-----------------|----------------|-------------------|
| Pipeline | High | Sequential (Slow) | High (Bubble) | Moderate (Activations) |
| Tensor | Low* | Parallel (Fast) | Low (Fast) | Very High (All-Reduce) |
| CFG | Moderate | Parallel | N/A | Low (Final Image) |

*Every node still needs full KV cache and base model overhead.

## 4. Device Topology / Capability Reporting

### Topology Discovery System

exo builds a **directed graph** representation of the cluster using `rustworkx.PyDiGraph` (a Python wrapper around a Rust graph library).

### Data Collection

| Gatherer | Source | Data Collected |
|----------|--------|----------------|
| `InfoGatherer` | `src/exo/utils/info_gatherer/info_gatherer.py` | CPU, GPU memory, network interfaces, Thunderbolt bridges |
| `net_profile` | `src/exo/utils/info_gatherer/net_profile.py` | Reachability, latency, bandwidth between nodes |
| `RdmaCtlStatus` | `src/exo/utils/info_gatherer/info_gatherer.py` | RDMA capability via `rdma_ctl` binary |
| `SystemInfo` | `src/exo/utils/info_gatherer/system_info.py` | OS, architecture, device type |

### Topology Graph Structure

```
Topology [rustworkx.PyDiGraph]
    |
    +-- NodeInfo (capabilities: memory, flops, device type)
    +-- Connection (edge: latency, bandwidth, is_thunderbolt, is_rdma)
```

**Key Operations**:
- `add_node(NodeInfo)`: Add node with performance profile.
- `add_connection(Connection)`: Add directed edge with link characteristics.
- `get_cycles()`: Find all simple cycles for pipeline parallelism placement.
- `get_cycles_tb()`: Find cycles using only Thunderbolt connections.
- `remove_node(NodeId)`: Remove failed node and all edges.

### Thunderbolt/RDMA Detection

On macOS, exo performs deep hardware inspection:
1. Parses `networksetup -listallhardwareports` to find Thunderbolt devices.
2. Maps bridge interfaces via `ifconfig`.
3. Checks `rdma_ctl` utility for RDMA enablement status.
4. Prioritizes network interfaces: Ethernet > WiFi > Thunderbolt Bridge.

### IP Prioritization

When building hostfiles for MLX Ring, exo ensures the fastest network path is used by analyzing interface types and testing reachability.

## 5. Fault Tolerance and Peer Disconnection

### Seniority-Based Leader Election

exo uses a **Bully-style election protocol** to automatically select a master node. All nodes participate.

**Election Triggers**:
- New node joins or existing node disconnects.
- Higher election clock received from another node.
- Node startup.

**Election Message**:
```python
ElectionMessage(
    clock: int,              # Round number; higher wins
    seniority: int,          # Prior winners get higher seniority
    proposed_session: SessionId,
    commands_seen: int       # Tiebreaker: more commands = higher priority
)
```

**Winner Selection** (priority order):
1. Higher `clock`
2. Higher `seniority`
3. More `commands_seen`
4. Lexicographically larger `node_id`

**Campaign Lifecycle** (3-second timeout):
1. Broadcast `ElectionMessage` to `ELECTION_MESSAGES` topic.
2. Wait 3 seconds collecting responses.
3. `elected = max(candidates)`.
4. If local node won: `seniority = max(seniority, len(participants))`.
5. Emit `ElectionResult` to orchestrator.

### Session Invalidation

`SessionId` contains `master_node_id` and `election_clock`. When a new master is elected, the clock increments, invalidating all prior sessions in the `EventRouter`. This prevents stale events from an old master from being processed.

### Runner/Task Recovery

| Layer | Failure Detection | Recovery Action |
|-------|-------------------|-----------------|
| **Worker** | `plan()` checks `state.runners` for `RunnerFailed` | Issues `Shutdown` task to stop the failed `RunnerSupervisor` |
| **Master** | Detects `InstanceDeleted` event in event log | Re-runs `place_instance()` to re-shard model on available nodes |
| **Node** | libp2p connection disconnect | Triggers new election; topology graph removes node and its edges |

### Deadlock Prevention

- `eval_with_timeout`: Wraps MLX evaluation. If an operation hangs beyond `timeout_seconds` (default 60s), the process is terminated to prevent cluster-wide GPU deadlocks.
- `RunnerSupervisor` monitors runner health. On distributed initialization failure, emits `RunnerStatusUpdated(RunnerFailed)`, causing Master to issue a `Shutdown` for the entire instance.

### Graceful Shutdown

The `Node` captures `SIGINT`/`SIGTERM`, cancels the primary `TaskGroup`, and propagates shutdown to:
- **Worker**: Closes event/command senders, shuts down `RunnerSupervisor` processes.
- **Master**: Closes `DiskEventLog` and channels.
- **DownloadCoordinator**: Cancels active download tasks.

## 6. Ring-Reduce / All-Reduce Communication Pattern

### MLX Ring Backend (TCP/IP)

The Ring backend implements **ring all-reduce and ring all-gather**:

- Nodes are connected in a logical ring: rank `i` connects only to `i-1` and `i+1`.
- `send()` and `recv()` only work between neighbors.
- For `all_sum()`, data is chunked and circulated around the ring, with each node accumulating partial sums, then the full result circulates back.

**Hostfile JSON** (auto-generated by exo):
```json
[
  {"ssh": "node0", "ips": ["10.0.0.1"]},
  {"ssh": "node1", "ips": ["10.0.0.2"]},
  {"ssh": "node2", "ips": ["10.0.0.3"]}
]
```

**Environment Variables**:
- `MLX_RANK`: 0-based rank of the process.
- `MLX_HOSTFILE`: Path to JSON hostfile.
- `MLX_RING_VERBOSE=1`: Enables debug logging.

### MLX Jaccl Backend (RDMA)

For tensor parallelism, Jaccl provides a **full mesh** of RDMA connections:

- Requires direct Thunderbolt 5 cables between all pairs of nodes.
- `MLX_IBV_DEVICES` JSON matrix defines the RDMA device for each `[i][j]` pair:
  ```json
  [
    [null, "rdma_en5", "rdma_en4", "rdma_en3"],
    ["rdma_en5", null, "rdma_en3", "rdma_en4"],
    ["rdma_en4", "rdma_en3", null, "rdma_en5"],
    ["rdma_en3", "rdma_en4", "rdma_en5", null]
  ]
  ```
- `MLX_JACCL_COORDINATOR`: IP:port of rank 0 for initial handshake.
- Enables `MLX_METAL_FAST_SYNCH=1` for faster CPU-GPU synchronization during communication.

### Collective Operations

MLX distributed provides these primitives (which exo uses internally):
- `mx.distributed.all_sum(x)`: All-reduce summation.
- `mx.distributed.all_gather(x)`: Concatenate tensors from all ranks.
- `mx.distributed.send(x, dst)` / `recv(src)`: Point-to-point (ring neighbors only in Ring backend).
- `mx.distributed.recv_like(x, src)`: Receive tensor matching shape of `x`.

### Synchronization

- `mx_barrier(group)`: Ensures all nodes reach the same execution point before sensitive operations (model loading, KV cache rotation).

## 7. Rust Implementations and Inspiration

### exo's Own Rust Components

exo is not a pure-Python project. It contains a **Rust networking crate** that can serve as direct reference architecture:

| Rust Component | Path | Purpose |
|----------------|------|---------|
| `networking` crate | `rust/networking/` | libp2p swarm management, mDNS discovery |
| `discovery.rs` | `rust/networking/src/discovery.rs` | Peer discovery logic |
| `swarm.rs` | `rust/networking/src/swarm.rs` | libp2p swarm event handling |
| `exo_pyo3_bindings` | `rust/exo_pyo3_bindings/` | PyO3 bindings exposing Rust networking to Python |
| `networking.rs` | `rust/exo_pyo3_bindings/src/networking.rs` | `NetworkingHandle` for Python-Rust interop |
| `allow_threading.rs` | `rust/exo_pyo3_bindings/src/allow_threading.rs` | Threading utilities for Python GIL |

### Key Rust Dependencies

- `libp2p` (Rust implementation): Peer-to-peer networking stack with mDNS, GossipSub, and swarm management.
- `pyo3`: Python-Rust bindings.
- `rustworkx` (Python package wrapping Rust): High-performance directed graph for topology.

### Other Projects for Inspiration

| Project | Language | Notes |
|---------|----------|-------|
| **exo-explore/exo** | Python + Rust | The primary reference. Hybrid architecture with Rust libp2p networking and Python MLX orchestration. |
| **mzbac/mlx_sharding** | Python | Distributed inference for MLX LLMs. Simpler than exo, good for understanding MLX sharding basics. |
| **llm-d/llm-d** | Go / Python | Kubernetes-native distributed inference. Not P2P; uses centralized scheduling. |
| **Meshcore** | (Concept) | Decentralized P2P LLM inference network concept (2026). Less mature than exo. |
| **rust-libp2p** | Rust | The networking stack exo uses. Can be studied independently for P2P mesh patterns. |

### Design Principles to Borrow for a Rust Implementation

1. **Hybrid architecture**: Rust for networking/discovery (libp2p), Rust/native for tensor execution, with a clear IPC boundary.
2. **Topic-based messaging**: GossipSub topics for decoupled control plane communication.
3. **Graph-based topology**: Directed graph with cycle detection for pipeline placement.
4. **Backend abstraction**: Abstract over `all_sum`/`all_gather` so TCP ring and RDMA mesh can be swapped.
5. **Event sourcing**: Ordered event log with session invalidation for consistency during failover.
6. **Seniority election**: Deterministic, convergence-guaranteed leader election without external coordination.
7. **Timeout-based deadlock prevention**: Every distributed MLX operation wrapped with a timeout.
